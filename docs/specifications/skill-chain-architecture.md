# Specification: Архітектура системи модульних скілів (Practical Agent Skills)

## 1. Призначення та Межі (Purpose & Scope)

Система **Practical Agent Skills** визначає набір із 12 модульних скілів для AI-агентів розробки, які забезпечують керований цикл інженерії програмного забезпечення — від формулювання сирої думки до реалізації коду за TDD, аудиту якості, підтримки актуальної документації та контролю версій.

### Ключові архітектурні цілі

1. **Ізоляція тимчасового стану розробки**: Усі проміжні артефакти планування (`intent.md`, `proposal.md`, `tasks.md`, `review-N-tasks.md`, `subtasks-N.md`) створюються виключно всередині `.temp/<topic>/`, яка ігнорується Git (`.gitignore`).
2. **Відокремлення планів від специфікацій**: Директорія `docs/specifications/` містить виключно декларативні нормативні описи того, як система працює зараз. Тимчасові плани рефакторингу чи списки задач ніколи не записуються у `docs/specifications/`.
3. **Суворий поділ ролей (Read-Only Advisors vs. Scoped Writers)**: Кожен скіл має чітко визначену зону відповідальності й дозволів доступу до файлової системи.
4. **Інтерактивні розвилки замість блокувань (Interactive Prerequisite & Forward Advisors)**: За відсутності попереднього етапу або після завершення роботи скіл пропонує варіанти дій із власною рекомендацією `(Recommended)` та підтримує діалог про плюси/мінуси перед вибором.

## 2. Базові контракти та Інтерфейси скілів (Core Contracts & Interfaces)

### 2.1. Матриця прав доступу всіх 12 скілів

| Скіл | Тип | Дозволені операції запису | Суворі заборони (`FORBIDDEN`) |
| :--- | :--- | :--- | :--- |
| **`/idea`** | Lifecycle (Stage 0) | **Жодних (100% Read-Only)** | Створення/зміна будь-яких файлів; допит про низькорівневий код до формування ідеї |
| **`/interview`** | Lifecycle (Stage 1) | **Жодних (100% Read-Only)** | Створення/зміна будь-яких файлів; пакетні опитування (>1 питання за хід); >5 питань загалом (залишок виноситься в `Assumptions`) |
| **`/intent`** | Lifecycle (Stage 2) | `.temp/<topic>/intent.md`, `.gitignore` | Зміна `src/`, `docs/`, кореневих файлів |
| **`/proposal`** | Lifecycle (Stage 3) | `.temp/<topic>/proposal.md`, `.gitignore` | Зміна `src/`, `docs/`; написання повного продуктового коду в RFC |
| **`/decompose`** | Lifecycle (Stage 4) | Нові файли `.temp/<topic>/tasks.md`, `review-N-tasks.md`, `subtasks-*.md`, `.gitignore` | Перезапис або редагування вже існуючих файлів задач; зміна `src/` чи `docs/` |
| **`/implement`** | Lifecycle (Stage 5) | Вихідний код і тести (`src/`), статус задач `[ ]` → `[x]` (виконано) або `[-]` (скасовано) в активному файлі задач | Видалення описів задач; зміна `docs/specifications/`; видалення `.temp/` |
| **`/review`** | Lifecycle (Stage 6) | **Жодних записів у вихідні/відстежувані файли (Zero-Write Auditor)**; дозволено read-only перевірки (`git diff`, тести в `--ci`, тайпчекер, лінтер без `--fix`) | Створення/редагування будь-яких вихідних файлів, снапшотів, `docs/` або `.temp/` (включно з `review-N-tasks.md`) |
| **`/spec`** | Lifecycle (Stage 7) | `docs/specifications/<name>.md`; запис про специфікацію в індексі документації проєкту (якщо він є) | Зміна `src/` або `.temp/`; запис історії міграцій або інструкцій «як змінити в майбутньому» у специфікацію; перенумерація наявних ID інваріантів |
| **`/cleanup`** | Lifecycle (Stage 8) | Видалення папок `.temp/<topic>/` після явного підтвердження (структурований інструмент запитань хоста або текстовий fallback) | Видалення без явного підтвердження користувача; видалення поза `.temp/` |
| **`/using-agent-skills`** | Meta-Router | **Жодних (100% Read-Only)** | Створення/зміна будь-яких файлів |
| **`/debug`** | Utility | Мінімальний фікс + регресійний тест після діагностики (або точкова інструментація для flaky-багів) | Хаотичне вгадування без відтворення і локалізації; додавання фіч при поламаному білді |
| **`/git`** | Utility | `git add`, `git commit` після підтвердження плану | Індексація/коміт `.temp/`; виконання `git commit` або `git push` без згоди користувача |

### 2.2. Протокол визначення активної теми (`.temp/<topic>/` Resolution) та Status/Resume Mode

Усі скіли, що працюють із `.temp/`, використовують єдиний детермінований алгоритм:

1. Якщо в `.temp/` існує рівно **1 папка теми** або назва теми однозначно випливає з поточного чату — тема обирається автоматично з виведенням рядка `Active topic: .temp/<topic>/`.
2. Якщо в `.temp/` існує **2 або більше папок тем** і з контексту чату неможливо однозначно визначити цільову тему — агент виводить перелік наявних тем і запитує користувача.
3. Перед створенням першого файлу в `.temp/` агент перевіряє, чи `.temp` вже ігнорується кореневим `.gitignore` (варіанти `.temp`, `.temp/`, `/.temp/`, з урахуванням CRLF), і додає `.temp/` лише один раз, без дублікатів.
4. **Status / Resume Mode (`/using-agent-skills`)**: У новій сесії роутер сканує `.temp/`, підраховує виконані `[x]`, скасовані `[-]` та активні `[ ]` задачі й вказує точну наступну задачу для відновлення роботи.

---

### 2.3. Протокол інтерактивних розвилок (Interactive Advisor Loop), Fast-Track та Autopilot

На вході (Prerequisite Advisor) та на виході (Forward Handoff) кожен скіл дотримується контракту:

1. Надає повний перелік релевантних варіантів дій та позначає оптимальний варіант як **`(Recommended)`** із коротким обґрунтуванням.
2. Дозволяє користувачу поставити уточнюючі запитання або запитати про плюси й мінуси варіантів; після надання пояснення агент **обов'язково повторно виводить варіанти для вибору**.
3. **Fast-Track маршрути**: Невеликі та середні задачі можуть минати `/interview`, `/intent` та `/proposal`, переходячи одразу в `/decompose`, який записує компактну шапку `## Context & Intent` безпосередньо на початок `.temp/<topic>/tasks.md`.
4. **Terminal Turn Rule & Autopilot Mode**: За замовчуванням після виведення розвилки агент негайно зупиняє свій хід. Якщо ж користувач явно запросив режим **Autopilot** (*«роби до кінця»*), агент автоматично переходить за рекомендованими гілками між скілами й зупиняється лише у випадку: (а) вердикту `CHANGES RECOMMENDED` у `/review`, (б) архітектурного блокера/падіння тестів, або (в) перед виконанням `git commit` чи видаленням `.temp/`.

### 2.4. Контракт еволюції коду та неруйнівної декомпозиції

1. **Стратегія інтеграції в `/proposal`**:
   * При зміні існуючих методів, класів або публічних контрактів агент пропонує вибір між:
     * **Parallel Implementation (Expand-Contract)**: створення нової реалізації поруч зі старою → перемикання клієнтів після повної готовності → визначення політики щодо старого коду (**Deprecate** або **Remove**).
     * **Direct In-Place Replacement**: пряма заміна (лише для локальних неруйнівних змін).
2. **Імутабельність, статуси та пріоритет файлів задач у `/decompose` та `/implement`**:
   * `/decompose` ніколи не перезаписує створені файли задач. Кожна нова ітерація створює окремий файл: `tasks.md` (первинний), `review-1-tasks.md`, `review-2-tasks.md` (за підсумками `/review`), `subtasks-<N>.md` або `subtasks-r<M>-<N>.md` (при дробленні задачі, із обов'язковим заголовком `Parent: <file>#Task <N>`).
   * Підтримуються три статуси чекбоксів: `- [ ]` (очікує виконання), `- [x]` (виконано і перевірено за суворим циклом TDD `Red → Green → Verify`), `- [-] ~~Task N~~ (cancelled: <причина>)` (скасовано/втратило актуальність).
   * `/implement` обирає активний файл із невирішеними задачами (`- [ ]`) за пріоритетом: `subtasks-*.md` → `review-<N>-tasks.md` (з найбільшим `N`) → `tasks.md`, і **не вичитує у контекст старі файли, де всі задачі вже закриті (`[x]` / `[-]`)**.
   * Коли в `subtasks-*.md` закривається остання задача (`[x]` або `[-]`), `/implement` за заголовком `Parent: <file>#Task <N>` автоматично синхронізує статус відповідної батьківської задачі (`[ ]` → `[x]`) у точному батьківському файлі.
   * Після виконання кожної окремої задачі проєкт залишається в 100% робочому стані (компілюється і проходить тести).

### 2.5. Контракт дистрибуції та встановлення репозиторію

Репозиторій підтримує як локальне (проєктне), так і глобальне встановлення з контролем цілісності через маніфест хешів (`.practical-agent-skills.manifest`):

* **`skills/<name>/SKILL.md`**: єдине канонічне джерело правди всіх 12 скілів для сумісності з `npx skills add` (локально та `--global`), `agy plugin install`, `gemini skills install` та скриптів `install.ps1` / `install.sh`.
* **`.agents/skills`**: Directory Junction (Windows) або Symlink (Linux/macOS) всередині репозиторію, який прямо вказує на `skills/` (створюється командою `.\install.ps1 -SyncRepo` або `./install.sh --sync-repo`; у PowerShell 5.1 видаляється виключно сам лінк через `.Delete()` без рекурсивного обходу цілі).
* **`plugin.json`**: кореневий маніфест плагіна Antigravity.
* **`install.ps1` / `install.sh`**: скрипти встановлення з повною паритетністю прапорців:
  * `-All` / `--all` — оновлення Junction/Symlink у репо, глобальних директорій та всіх сусідніх проєктів із `.agents/skills`;
  * `-Global` / `--global`, `-Target <path>` / `--target <path>`, `-Skill <name>` / `--skill <name>`, `-SyncRepo` / `--sync-repo`;
  * `-Force` / `--force` — перезапис локально модифікованих скілів (за замовчуванням модифіковані вручну скіли пропускаються з попередженням за SHA-256 хешем у `.practical-agent-skills.manifest`);
  * `-Prune` / `--prune` — видалення застарілих/перейменованих скілів, які раніше були встановлені скриптом, але більше не існують у `skills/` (кастомні скіли проєкту поза маніфестом ніколи не чіпаються).

## 3. Інваріанти поведінки (Behavioral Invariants)

* **Always**:
  * Спілкуватися з користувачем і створювати артефакти в `.temp/` мовою звернення користувача; вести `docs/specifications/` мовою документації проєкту.
  * Перевіряти точні версії бібліотек у маніфестах проєкту (`package.json`, `.csproj`, `Cargo.toml`, `pyproject.toml`, `go.mod`) перед проектуванням (`/proposal`) або написанням коду (`/implement`).
  * У `/implement` запускати новий тест **до** написання коду реалізації (фаза **Red**), щоб переконатися, що тест падає з очікуваної причини.
  * Зберігати проєкт у 100% робочому стані після кожної окремої задачі.
  * Брати факти про конкретний проєкт (команди збірки й тестів, конвенції коду, правила комітів, формат специфікацій) з його власних інструкцій (`AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, hooks, наявні документи); скіли залишаються проєктно-незалежними.
  * У делегованому (subagent) або неінтерактивному режимі не виводити розвилки, а явно фіксувати припущення, зупинятися на блокерах і ніколи не підтверджувати автоматично коміт, push чи видалення `.temp/`.
* **Never**:
  * Ніколи не створювати тимчасові файли розробки (`SPEC.md`, `tasks/`, `docs/intent/`) поза `.temp/<topic>/`.
  * Ніколи не виконувати запис або видалення вихідних чи відстежуваних файлів під час роботи read-only / zero-write скілів (`/idea`, `/interview`, `/review`, `/using-agent-skills`).
  * Ніколи не індексувати і не комітити директорію `.temp/` у Git.
