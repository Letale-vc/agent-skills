# Specification: Архітектура системи модульних скілів (Practical Agent Skills)

## 1. Призначення та Межі (Purpose & Scope)

Система **Practical Agent Skills** визначає набір модульних скілів для AI-агентів розробки, які забезпечують керований цикл інженерії програмного забезпечення — від формулювання сирої думки до реалізації коду за TDD, аудиту якості, підтримки актуальної документації та контролю версій.

Цей документ фіксує лише **контракти між скілами** (права доступу, робочий простір, ворота, формат файлів задач) і дистрибуцію репозиторію. Поведінку окремого скіла визначає його `skills/<name>/SKILL.md`; у разі розбіжності джерелом правди є `SKILL.md`, а цей документ оновлюється під нього.

### Ключові архітектурні цілі

1. **Ізоляція тимчасового стану розробки**: усі проміжні артефакти планування створюються виключно в `.temp/<topic>/`, яка ігнорується Git.
2. **Відокремлення планів від специфікацій**: `docs/specifications/` містить лише декларативні описи того, як система працює зараз; плани рефакторингу й списки задач туди не потрапляють.
3. **Суворий поділ ролей**: кожен скіл має чітку зону відповідальності й права доступу до файлової системи (2.1).
4. **Default-Proceed замість меню та блокувань**: безпечні кроки виконуються без запитань; користувача питають лише на воротах (2.3).

## 2. Контракти між скілами (Cross-Skill Contracts)

### 2.1. Матриця прав доступу

| Скіл | Тип | Дозволені записи | Суворі заборони (`FORBIDDEN`) |
| :--- | :--- | :--- | :--- |
| **`/idea`**, **`/interview`**, **`/using-agent-skills`** | Read-Only | **Жодних** | Створення/зміна будь-яких файлів; команди, що змінюють стан проєкту |
| **`/review`**, **`/audit`**, **`/architect`** | Zero-Write Auditor | **Жодних**; дозволено read-only перевірки (збірка, тести без оновлення снапшотів, тайпчекер, лінтер без `--fix`, `git diff`/`log`/`blame`, інструменти залежностей проєкту) | Створення/зміна будь-яких файлів, зокрема `.temp/`; команди, що змінюють дерево або встановлюють пакети |
| **`/proposal`** | Writer | `.temp/<topic>/proposal.md`, `.gitignore` | Зміна `src/`, `docs/`; повний продуктовий код у RFC |
| **`/decompose`** | Append-Writer | Нові файли задач у `.temp/<topic>/`, `.gitignore` | Перезапис чи редагування наявних файлів задач; зміна `src/`, `docs/` |
| **`/implement`** | Writer | Код і тести; статуси `[x]` / `[-]` у файлах задач | Видалення описів задач; зміна `docs/specifications/`; видалення `.temp/` |
| **`/debug`** | Diagnostic & Fix | Мінімальний фікс + регресійний тест (або точкова інструментація для flaky-багів) | Фікс без відтворення й локалізації; нові фічі при поламаному білді |
| **`/spec`** | Writer | `docs/specifications/<name>.md`; запис у документаційному індексі проєкту | Зміна `src/` або `.temp/`; історія міграцій у специфікації; перенумерація ID інваріантів |
| **`/git`** | Git Operator | `git add`, `git commit` після підтвердження плану | Коміт `.temp/`; `git commit` / `git push` без згоди користувача |
| **`/cleanup`** | Cleaner | Видалення `.temp/<topic>/` після явного підтвердження | Видалення без підтвердження або поза `.temp/` |

---

### 2.2. Робочий простір `.temp/<topic>/`

1. **Артефакти та їхні автори**: `proposal.md` (`/proposal`, разом із метою, критеріями успіху й межами теми), `tasks.md`, `review-<N>-tasks.md`, `subtasks-<N>.md` / `subtasks-r<M>-<N>.md` (`/decompose`). Інші скіли ці файли лише читають; `/implement` змінює тільки статуси задач.
2. **Визначення теми**: рівно одна тема або тема, очевидна з чату, обирається автоматично з рядком `Active topic: .temp/<topic>/`; за 2+ тем і неоднозначності агент питає користувача.
3. **`.gitignore`**: перед першим записом у `.temp/` агент перевіряє, чи `.temp` уже ігнорується (варіанти `.temp`, `.temp/`, `/.temp/`, з урахуванням CRLF), і додає `.temp/` лише один раз.
4. **Git worktree**: `.temp/` у worktree немає; джерелом правди є `.temp/<topic>/` основного checkout'у.
   * Субагент у worktree отримує повний текст задачі та шапку `## Context & Intent` у промпті й не торкається `.temp/`; чекбокси оновлює оркестратор в основному checkout'і.
   * Скіл, що сам працює у worktree (`git rev-parse --git-dir` ≠ `git rev-parse --git-common-dir`), один раз копіює папку теми в `.temp/` worktree і пише лише туди, ніколи в основний checkout за абсолютним шляхом.
5. **Status Mode** (`/using-agent-skills`): сканує `.temp/`, рахує `[x]` / `[-]` / `[ ]` і називає точну наступну задачу та рекомендований скіл.

---

### 2.3. Default-Proceed, ворота (Gates) та Autopilot

1. **Безпечний і зворотний крок виконується без меню** з оголошенням в один рядок мовою користувача (*«→ Далі: `/review` (рекомендовано). Напиши «стоп», щоб змінити.»*): read-only робота, запис у `.temp/<topic>/`, вибір очевидної теми, `/implement` у Batch-режимі на затвердженому файлі задач.
2. **Ворота** — агент зупиняє хід і ставить одне коротке питання (рекомендована відповідь першою, не більше 3 варіантів):
   1. **Незворотні дії**: `git commit`, `git push`, `git tag`, деструктивні git-команди, видалення `.temp/<topic>/`.
   2. **Рішення користувача**: конфлікт вимог і коду, архітектурна неоднозначність, ламання публічного контракту, нова залежність.
   3. **Збої**: падіння збірки/тестів, не виправлене за 3 спроби, або вердикт `CHANGES RECOMMENDED`.
   4. **Ручні перевірки**: крок, який може виконати чи побачити лише користувач.
   5. **Чекпоінти**: затвердження нового `proposal.md` і старт змін коду для нового файлу задач.
3. **Autopilot** (на явний запит, *«роби до кінця»*): агент проходить також чекпоінти (5); ворота 1–4 зупиняють виконання завжди.
4. **Fast-Track**: невеликі задачі минають `/interview` і `/proposal`, а `/decompose` записує компактну шапку `## Context & Intent` на початок `tasks.md`.

### 2.4. Контракт файлів задач (`/decompose` → `/implement`, `/review`, `/cleanup`, Status Mode)

1. **Незмінність**: `/decompose` ніколи не перезаписує наявні файли задач; кожна нова ітерація — окремий файл.
2. **Статуси**: `- [ ]` (очікує), `- [x]` (виконано й перевірено), `- [-] ~~Task N~~ (cancelled: <причина>)` (скасовано; вважається закритою).
3. **Активний файл**: `/implement` обирає файл із `- [ ]` за пріоритетом `subtasks-*.md` → `review-<N>-tasks.md` (найбільший `N`) → `tasks.md` і не читає повністю закриті файли.
4. **Поля задачі, які читають інші скіли**:
   * `**Model**: high | standard` — рівень моделі для делегованого виконання; конкретну модель визначають інструкції проєкту (напр., у Claude Code `high` → `opus`, `standard` → `sonnet`); явна вказівка користувача має пріоритет, відсутній тег вважається `high`.
   * `Manual check:` — `/implement` у Batch-режимі зупиняється після автоматизованих кроків і дає користувачу чекліст.
   * `**Design**: /proposal first in .temp/<own-topic>/` — дизайн задачі ще не узгоджено: `/implement` зупиняється перед нею й рекомендує `/proposal` у названій темі.
   * `Parent: <file>#Task <N>` — у `subtasks-*.md` і в `tasks.md` теми, відкритої для задачі з `**Design**:` (шлях може вести в іншу тему); коли в такому файлі закривається остання задача, `/implement` позначає батьківську задачу `[x]`.
5. **Робочий стан**: після кожної задачі проєкт компілюється і проходить тести.
6. **Стратегія інтеграції**: `/proposal` (або шапка `tasks.md`) фіксує **Expand-Contract** чи **In-Place**; від цього залежать порядок задач у `/decompose` і розділ застарілих інтерфейсів у `/spec`.
7. **Рев'ю**: після закриття всіх задач `/implement` переходить до `/review`, за можливості хоста — в окремому субагенті зі свіжим контекстом; ворота вердикту (`CHANGES RECOMMENDED`) показує основна сесія.
8. **Дорожня карта `/architect`**: обрані кроки `/decompose` записує в `.temp/arch-<area>/tasks.md` (цільові правила залежностей — у `Constraints` шапки), крок із відкритим дизайном стає задачею з `**Design**:`. Після реалізації `/review` веде до `/spec` навіть для внутрішньої перебудови, а `/spec` фіксує правила залежностей, яких код уже дотримується, як інваріанти.

### 2.5. Контракт дистрибуції та встановлення репозиторію

Репозиторій підтримує як локальне (проєктне), так і глобальне встановлення з контролем цілісності через маніфест хешів (`.practical-agent-skills.manifest`):

* **`skills/<name>/SKILL.md`**: єдине канонічне джерело правди всіх скілів для сумісності з `npx skills add` (локально та `--global`), `agy plugin install`, `gemini skills install` та скриптів `install.ps1` / `install.sh`.
* **`skills/<name>/evals/`**: тестові випадки скіла у форматі `claude plugin eval`; `install.ps1` / `install.sh` ніколи не копіюють цю папку і не враховують її в хеші маніфесту.
* **`.agents/skills`**: Directory Junction (Windows) або Symlink (Linux/macOS) всередині репозиторію, який прямо вказує на `skills/` (створюється командою `.\install.ps1 -SyncRepo` або `./install.sh --sync-repo`; у PowerShell 5.1 видаляється виключно сам лінк через `.Delete()` без рекурсивного обходу цілі).
* **`plugin.json`**: кореневий маніфест плагіна Antigravity.
* **`install.ps1` / `install.sh`**: скрипти встановлення з повною паритетністю прапорців:
  * `-All` / `--all` — оновлення Junction/Symlink у репо, глобальних директорій та всіх сусідніх проєктів із `.agents/skills`;
  * `-Global` / `--global`, `-Target <path>` / `--target <path>`, `-Skill <name>` / `--skill <name>`, `-SyncRepo` / `--sync-repo`;
  * `-Force` / `--force` — перезапис локально модифікованих скілів (за замовчуванням модифіковані вручну скіли пропускаються з попередженням за SHA-256 хешем у `.practical-agent-skills.manifest`);
  * `-Prune` / `--prune` — видалення застарілих/перейменованих скілів, які раніше були встановлені скриптом, але більше не існують у `skills/` (кастомні скіли проєкту поза маніфестом ніколи не чіпаються).

## 3. Інваріанти поведінки (Behavioral Invariants)

* **Always**:
  * Спілкуватися з користувачем і створювати артефакти в `.temp/` мовою звернення користувача; вести `docs/specifications/` мовою документації проєкту.
  * Перевіряти точні версії бібліотек у маніфестах проєкту (`package.json`, `.csproj`, `Cargo.toml`, `pyproject.toml`, `go.mod`) перед проєктуванням (`/proposal`) або написанням коду (`/implement`).
  * Зберігати проєкт у 100% робочому стані після кожної окремої задачі.
  * Брати факти про конкретний проєкт (команди збірки й тестів, конвенції коду, правила комітів, формат специфікацій) з його власних інструкцій (`AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, hooks, наявні документи); скіли залишаються проєктно-незалежними.
  * У делегованому (subagent) або неінтерактивному режимі не виводити розвилки, а явно фіксувати припущення, зупинятися на блокерах і ніколи не підтверджувати автоматично коміт, push чи видалення `.temp/`.
  * Виконувати безпечні й зворотні рекомендовані кроки без меню, зупиняючись лише на воротах (2.3).
* **Never**:
  * Ніколи не виконувати `git commit`, `git push` чи видалення `.temp/` без явного підтвердження користувача, зокрема в режимі Autopilot.
  * Ніколи не писати в основний checkout за абсолютним шляхом під час роботи у git worktree.
  * Ніколи не створювати тимчасові файли розробки (`SPEC.md`, `tasks/`, `docs/intent/`) поза `.temp/<topic>/`.
  * Ніколи не виконувати запис або видалення файлів під час роботи read-only / zero-write скілів (2.1).
  * Ніколи не індексувати і не комітити директорію `.temp/` у Git.
