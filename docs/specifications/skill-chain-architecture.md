# Specification: Архітектура ланцюжка скілів (плагін `pas`)

## 1. Призначення та межі

**Practical Agent Skills** — плагін Claude Code `pas` (marketplace `letale-skills`), який веде інженерну роботу від сирої ідеї до коміту: маршрут за розміром задачі, TDD-реалізація субагентами, рев'ю, нормативні специфікації й контроль версій. Для інших агентів (Codex, Antigravity тощо) той самий вміст ставлять скрипти встановлення (§3.8).

Документ фіксує лише **контракти між частинами плагіна**: склад, права доступу, маршрути, робочий простір, ворота, формат файлів задач, делегування й дистрибуцію. Поведінку окремого скіла чи агента визначає його файл (`skills/<name>/SKILL.md`, `agents/<name>.md`), спільні правила — `shared/*.md`; у разі розбіжності джерелом правди є ці файли, а специфікація оновлюється під них.

## 2. Склад плагіна

| Частина | Вміст | Роль |
| --- | --- | --- |
| `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` | маніфест плагіна `pas` і marketplace `letale-skills` з одним плагіном (`source: "./"`) | дистрибуція в Claude Code |
| `skills/` (10) | `flow`, `shape`, `proposal`, `decompose`, `implement`, `review`, `debug`, `spec`, `git`, `audit` (+ `audit/structure.md`) | кроки ланцюжка; виклик `/pas:<name>` |
| `agents/` (6) | `scout`, `architect`, `decomposer`, `implementer`, `reviewer`, `spec-writer` | субагенти зі свіжим контекстом; ім'я `pas:<name>` |
| `shared/` (3) | `rules.md` (режими, `.temp/`, теми, worktree, ворота, поведінка, перевикористання, гігієна контексту, мова), `complexity.md` (маршрути, оцінка складності, бюджет контексту), `task-template.md` (формат файлу задач) | єдина копія спільних правил |
| `hooks/hooks.json`, `scripts/` | `SessionStart` (`startup\|clear\|compact`): список незавершених тем `.temp/`; `PreToolUse` (`Bash\|PowerShell`): блокування force push, `reset --hard`, `git clean`, `--no-verify` | автоматичні захисти |

* Скіли й агенти посилаються на спільні файли як `${CLAUDE_PLUGIN_ROOT}/shared/<file>.md` і `${CLAUDE_PLUGIN_ROOT}/agents/<file>.md` і не повторюють їхній зміст.
* Скіли й агенти проєктно-незалежні: команди збірки й тестів, повна перевірка (full check), правила розміщення файлів, калібрування оцінки та моделі беруться з `CLAUDE.md` / `AGENTS.md` проєкту, і ці інструкції мають пріоритет.
* Текст скілів і агентів — англійською; мову чату задають інструкції проєкту.

## 3. Контракти

### 3.1. Режими й права доступу

| Скіл / агент | Режим | Дозволені записи |
| --- | --- | --- |
| `shape`, `audit`; агенти `scout`, `architect`, `reviewer` | read-only | жодних, зокрема `.temp/`; дозволено read-only перевірки (тести, збірка, тайпчекер, лінтер без `--fix`, `git diff` / `log` / `blame`) і кеші збірки |
| `proposal` | writes `.temp/` | `.temp/<topic>/proposal.md`, `.gitignore` (guard) |
| `review` | writes `.temp/` | лише `.temp/<topic>/review-<N>.md` (вердикт і нумеровані знахідки), `.gitignore` (guard); агенти `reviewer` лишаються read-only |
| `decompose`; агент `decomposer` | writes `.temp/` | лише **нові** файли задач у `.temp/<topic>/`, `.gitignore` (guard) |
| `flow` | conductor | `.temp/<topic>/flow.md`; на середньому маршруті — `.temp/<topic>/tasks.md`; решту записів роблять скіли й агенти етапів зі своїми правами |
| `implement`, `debug`; агент `implementer` | writes code | код і тести задачі; статуси чекбоксів (лише оркестратор) |
| `spec`; агент `spec-writer` | writes docs | `docs/specifications/*.md` і запис у документаційному індексі проєкту |
| `git` | git operator | `git add <paths>`, `git commit`, видалення `.temp/<topic>/` — лише після воріт 1 |

Поки хост має субагентів, головна сесія в `flow` / `implement` не редагує код, тести й `docs/` і робить не більше трьох прямих пошуків на питання, решту віддає `pas:scout`; це має пріоритет над дозволом проєкту редагувати 1–2 файли самій. Баг під час `flow` досліджує `pas:scout`, виправляє `pas:implementer` у режимі debug. Без субагентів кожен скіл працює в головній сесії за файлом відповідного агента зі своїм режимом.

### 3.2. Маршрути за розміром (`shared/complexity.md` §1)

| Розмір | Коли | Маршрут |
| --- | --- | --- |
| **Малий** | одна-дві задачі, баг | задача в промпті → `pas:implementer` (або `/pas:debug`) → повна перевірка (full check); без теми в `.temp/`, без `flow.md`, без рев'ю |
| **Середній** | до ~5 задач у наявних модулях, без нового публічного контракту, проєкту, шару чи `S2`-дизайну | головна сесія пише `.temp/<topic>/tasks.md` → батч `implementer` → повна перевірка (full check) → один `pas:reviewer` → `/pas:spec`, лише якщо змінилась специфікована поведінка → `/pas:git` |
| **Великий** | новий публічний контракт, проєкт чи шар, робота між шарами або понад ~5 задач | `/pas:shape` (якщо ціль неясна) → `/pas:proposal` (2–3 `pas:architect` паралельно, вибір користувача) → `pas:decomposer` → батчі `implementer` → повна перевірка (full check) → два `pas:reviewer` паралельно (correctness; simplicity+conventions) → `pas:spec-writer`, якщо є `docs/specifications/` → `/pas:git` |

Маршрут обирає `/pas:flow` і оголошує одним рядком; за сумніву між двома розмірами береться менший. Падіння тесту, краш чи регресія йдуть у `/pas:debug`; питання про структуру коду — у `/pas:audit structure`.

### 3.3. Робочий простір `.temp/<topic>/`

1. **Артефакти та автори**: `proposal.md` (`proposal`), `review-<N>.md` (`review`), `tasks.md`, `review-<N>-tasks.md`, `subtasks-<N>.md` / `subtasks-r<M>-<N>.md` (`decompose` / `decomposer`; `tasks.md` середнього маршруту — `flow`), `flow.md` (`flow`). Інші частини ці файли лише читають; оркестратор `implement` змінює тільки статуси задач.
2. **Тема**: названа в аргументах або очевидна з чату → вона; рівно одна папка → вона; кілька без збігу → питання (агент повертає `blocked:`). Рядок `Active topic: .temp/<topic>/` друкується один раз.
3. **`.gitignore` guard**: перед першим записом у `.temp/` перевіряється, чи `.temp` уже ігнорується (`.temp`, `.temp/`, `/.temp/`, з урахуванням CRLF); `.temp/` дописується один раз.
4. **Worktree**: джерелом правди є `.temp/<topic>/` основного checkout'у. Субагент у worktree отримує повний текст задачі й шапку `## Context & Intent` у промпті й не торкається `.temp/`; сесія, що сама працює у worktree, один раз копіює папку теми у свій `.temp/` і ніколи не пише в основний checkout за абсолютним шляхом.

### 3.4. Default-proceed і ворота (`shared/rules.md` §5)

1. Безпечний і зворотний крок (read-only робота, запис у `.temp/<topic>/`, очевидний вибір теми, батч на вже затвердженому файлі задач, створення гілки `feat/<topic>`) виконується без меню з оголошенням в один рядок.
2. **Ворота** — одне коротке питання, рекомендована відповідь першою, не більше трьох варіантів:
   1. **коміт або видалення**: `git commit` / `push` / `tag`, деструктивні git-команди, видалення `.temp/<topic>/`;
   2. **рішення дизайну**: конфлікт вимог із кодом чи специфікацією, архітектурна неоднозначність, ламання публічного контракту, нова залежність, вибір варіанту proposal;
   3. **знахідки рев'ю**: вердикт `CHANGES RECOMMENDED`, користувач обирає, що виправляти;
   4. **ручна перевірка**: крок, який може виконати чи побачити лише користувач;
   5. **збій**: збірка чи тести, не виправлені за 3 спроби.
3. «Роби до кінця» / autopilot не проходить жодних воріт. Субагент не питає користувача: фіксує припущення, на воротах і неоднозначностях повертає `blocked: <питання>`; ворота 1 автоматично не проходяться ніколи.

### 3.5. Контракт файлів задач (`shared/task-template.md`)

1. **Незмінність**: файл задач ніколи не перезаписується; нова розбивка — новий файл. Змінюються лише статуси.
2. **Статуси**: `- [ ]` (очікує), `- [x]` (виконано й перевірено), `- [-] ~~**Task N: …**~~ (cancelled: <причина>)` (скасовано, вважається закритою).
3. **Шапка**: `tasks.md` починається з `## Context & Intent` (`Goal`, `Strategy`: In-Place | Expand-Contract, `Constraints`); файл підзадач має рядок `Parent: <file>#Task N`.
4. **Поля задачі**: `**Model**: <tag> (D<n> V<n> S<n>)`, `Target files`, `Context`, `Reuse`, `Verification`; необов'язкові `Manual check` і `**Design**: proposal first in .temp/<own-topic>/` (замість `Target files`, `Context`, `Verification`).
5. **Активний файл** для `implement`: перший із `- [ ]` у порядку `subtasks-*.md` → найбільший `review-<N>-tasks.md` → `tasks.md`; повністю закриті файли не читаються.
6. **Ручні перевірки** не зупиняють батч: збираються й показуються одним чеклістом наприкінці (ворота 4), раніше — лише коли наступна задача залежить від результату.
7. **Задача з `Design`**: батч зупиняється перед нею й рекомендує `/pas:proposal` у названій темі; коли в темі з `Parent:` закривається остання задача, батьківська позначається `[x]`.
8. **Робочий стан**: після кожної задачі проєкт збирається, його тести зелені.

### 3.6. Делегування й модель (`shared/complexity.md` §2)

1. Кожна задача має оцінку D (рішення), V (перевірка), S (стан) від 0 до 2; сума й максимуми визначають тег і модель `implementer` (від sonnet `medium` до opus `xhigh`). Задача без оцінки виконується на opus `high`; явна вказівка користувача має пріоритет; проєкт може перевизначити відображення у своїх інструкціях.
2. `implementer` не має моделі у frontmatter: модель і effort задаються при спавні з оцінки. Інші агенти мають модель у визначенні: `scout` haiku; `architect`, `decomposer`, `reviewer` opus `high`; `spec-writer` sonnet `high`.
3. **Ескалація**: `blocked:` або червона перевірка після звіту `implementer` нижче opus `high` → одна повторна спроба на opus `high` зі зміною тегу задачі на `high`.
4. Промпт агента містить повний текст задачі й шапку `## Context & Intent` (або уривок `proposal.md`), ніколи міркування головної сесії. Звіт агента перевіряється перед тим, як йому довіряти.
5. **Перевірки**: `implementer` запускає перевірку проєкту, відфільтровану на зачеплені області, і повна перевірка (full check) лише на прохання промпту. Повний повна перевірка виконується один раз на батч. Перевірку, яку агент уже звітував зеленою на файлах, що відтоді не змінились, головна сесія не повторює, а читає з його звіту.
6. **Рев'ю**: `reviewer` звітує лише знахідки з упевненістю ≥ 80 із `path:line`, без pre-existing і того, що ловить компілятор чи лінтер. `CHANGES RECOMMENDED` — лише за хоча б однієї Critical або Major; самі Minor дають `APPROVED WITH NOTES`, який ланцюжок не зупиняє. `/pas:review` зберігає вердикт і нумеровані знахідки в `review-<N>.md`, тож відповідь «fix 1,3» працює й у новій сесії.

### 3.7. Диригент `/pas:flow` і `flow.md`

1. **Вхід**: без аргументу або з питанням про стан («де я зупинився», «що далі») — статус (теми `.temp/`, лічильники задач, `Stage` / `Next` із `flow.md`, один рекомендований крок; нічого не виконує); наявна тема — відновлення; інше — нова ціль із вибором маршруту (§3.2).
2. **Етапи**: `shape` → `proposal` → `decompose` → `implement` → `verify` → `review` → `spec` → `git` → `done`; середній маршрут починає з `implement`. Після кожного етапу оновлюється шапка `flow.md` (`Stage` — етап, що виконується наступним, `Active task file`, `Next`) і дописується рядок у `## Log`; рішення користувача — у `## Decisions`.
3. **Відновлення**: `/pas:flow <topic>` продовжує з `Stage`; коли артефакти показують пізніший прогрес, правда за артефактами. `Owner` називає сесію, що веде прогін. Сесія, що очищається, останнім рядком `Log` пише `Handoff: <наступний крок>`; після такого рядка нова сесія перебирає прогін без питання. Питання (ворота 2) — лише за ознак іншої живої сесії без handoff.
4. **Бюджет контексту** (`shared/complexity.md` §3): великий прогін завжди очищає сесію після `decompose`; будь-який — на ~300k токенів. Перед очищенням увесь потрібний стан записується в `.temp/<topic>/`, у `Log` дописується `Handoff: <наступний крок>`, користувач отримує одне повідомлення для продовження (`/pas:flow <topic>`).
5. `flow.md` — тонкий журнал до ~60 рядків: без чекбоксів і тексту задач.

### 3.8. Дистрибуція

* **Claude Code**: `claude plugin marketplace add Letale-vc/agent-skills` (або локальний шлях) і `claude plugin install pas@letale-skills`; для проєкту — `extraKnownMarketplaces` і `enabledPlugins: {"pas@letale-skills": true}` у `.claude/settings.json`. Проєктні `.claude/agents/` з тими самими іменами затіняють агенти плагіна.
* **Інші агенти** — `install.ps1` / `install.sh` з однаковими прапорцями (`-All`, `-Global`, `-Target`, `-Skill`, `-SyncRepo`, `-Force`, `-Prune`):
  * копіюють `skills/<name>/` без `evals/` у `<skills-dir>` (`<project>/.agents/skills`, `~/.agents/skills`, `~/.gemini/config/skills`), а `shared/` і `agents/` — у `<skills-dir>/../pas/`;
  * у кожному скопійованому файлі `${CLAUDE_PLUGIN_ROOT}` замінюється на `.agents/pas` (проєктне встановлення, шлях від кореня проєкту) або на абсолютний шлях `<skills-dir>/../pas` (глобальне);
  * `.practical-agent-skills.manifest` у `<skills-dir>` зберігає хеш кожного скіла у встановленому вигляді (без `\r`, після заміни): локально змінений скіл пропускається без `-Force`; скіл, якого більше немає в `skills/`, видаляє лише `-Prune`; скіли поза маніфестом не чіпаються; `pas/shared` і `pas/agents` належать інсталятору й замінюються щоразу;
  * `-Claude` нічого не копіює: друкує дві команди плагіна, а з `-Prune` видаляє з `.claude/skills` скіли, які туди раніше скопіював інсталятор (локально змінені — лише з `-Force`).
* **`skills/<name>/evals/`** — тестові випадки у форматі `claude plugin eval`; не встановлюються й не враховуються в хеші.
* **`plugin.json`** у корені — маніфест для Antigravity; `.agents/skills` у репозиторії — Junction / Symlink на `skills/` (`-SyncRepo`).

## 4. Інваріанти

* **INV-01**: спільне правило існує в одному файлі `shared/`; скіли й агенти посилаються на нього через `${CLAUDE_PLUGIN_ROOT}` і не повторюють.
* **INV-02**: скіли й агенти не містять назв, шляхів, команд чи прикладів конкретного проєкту; проєктні факти беруться з його інструкцій.
* **INV-03**: тимчасові файли розробки існують лише в `.temp/<topic>/`; `.temp/` ніколи не індексується й не комітиться; `docs/specifications/` описує лише поточний стан, без планів і історії.
* **INV-04**: read-only скіли й агенти (§3.1) не створюють, не змінюють і не видаляють жодних файлів.
* **INV-05**: `git commit`, `push` і видалення `.temp/<topic>/` відбуваються лише після явної згоди користувача на воротах 1, зокрема в `/pas:flow` і в субагентах.
* **INV-06**: файл задач ніколи не перезаписується; змінюються лише статуси чекбоксів, і лише оркестратором.
* **INV-07**: `flow.md` пише лише `/pas:flow`, без чекбоксів і тексту задач; скіли етапів не залежать від його існування.
* **INV-08**: після кожної задачі проєкт збирається, його тести зелені.
* **INV-09**: субагент ніколи не питає користувача: він повертає `blocked: <питання>` і перелік припущень.
* **INV-10**: при роботі у git worktree ніщо не пишеться в основний checkout за абсолютним шляхом.
* **INV-11**: встановлений скриптами скіл не містить `${CLAUDE_PLUGIN_ROOT}`: кожне посилання веде на наявний файл у `pas/shared` або `pas/agents`.
