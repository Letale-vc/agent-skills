# Specification: Архітектура системи модульних скілів (Practical Agent Skills)

## 1. Призначення та Межі (Purpose & Scope)

Система **Practical Agent Skills** визначає набір із 12 модульних скілів для AI-агентів розробки, які забезпечують керований цикл інженерії програмного забезпечення — від формулювання сирої думки до реалізації коду за TDD, аудиту якості, підтримки актуальної документації та контролю версій.

### Ключові архітектурні цілі

1. **Ізоляція тимчасового стану розробки**: Усі проміжні артефакти планування (`intent.md`, `proposal.md`, `tasks.md`, `review-N-tasks.md`, `subtasks-N.md`) створюються виключно всередині `.temp/<topic>/`, яка ігнорується Git (`.gitignore`).
2. **Відокремлення планів від специфікацій**: Директорія `docs/specifications/` містить виключно декларативні нормативні описи того, як система працює зараз. Тимчасові плани рефакторингу чи списки задач ніколи не записуються у `docs/specifications/`.
3. **Суворий поділ ролей (Read-Only Advisors vs. Scoped Writers)**: Кожен скіл має чітко визначену зону відповідальності й дозволів доступу до файлової системи.
4. **Інтерактивні розвилки замість блокувань (Interactive Prerequisite & Forward Advisors)**: За відсутності попереднього етапу або після завершення роботи скіл пропонує варіанти дій із власною рекомендацією `(Recommended)` та підтримує діалог про плюси/мінуси перед вибором.

## 2. Базові контракти та Інтерфейси скілів (Core Contracts & Interfaces)

### 2.1. Матриця прав доступу всіх 12 скілів

| Скіл | Тип | Дозволені операції запису | Суворі заборони (`FORBIDDEN`) |
| :--- | :--- | :--- | :--- |
| **`/idea`** | Lifecycle (Stage 0) | **Жодних (100% Read-Only)** | Створення/зміна будь-яких файлів; допит про низькорівневий код до формування ідеї |
| **`/interview`** | Lifecycle (Stage 1) | **Жодних (100% Read-Only)** | Створення/зміна будь-яких файлів; пакетні опитування (>1 питання за хід) |
| **`/intent`** | Lifecycle (Stage 2) | `.temp/<topic>/intent.md`, `.gitignore` | Зміна `src/`, `docs/`, кореневих файлів |
| **`/proposal`** | Lifecycle (Stage 3) | `.temp/<topic>/proposal.md`, `.gitignore` | Зміна `src/`, `docs/`; написання повного продуктового коду в RFC |
| **`/decompose`** | Lifecycle (Stage 4) | Нові файли `.temp/<topic>/tasks.md`, `review-N-tasks.md`, `subtasks-N.md`, `.gitignore` | Перезапис або редагування вже існуючих файлів задач; зміна `src/` чи `docs/` |
| **`/implement`** | Lifecycle (Stage 5) | Вихідний код і тести (`src/`), чекбокси `[ ]` → `[x]` в активному файлі задач | Переписування тексту умов задач; зміна `docs/specifications/`; видалення `.temp/` |
| **`/review`** | Lifecycle (Stage 6) | **Жодних (100% Read-Only)** | Створення/редагування будь-яких файлів (включно з `review-N-tasks.md`); запуск тестів |
| **`/spec`** | Lifecycle (Stage 7) | `docs/specifications/<name>.md` | Зміна `src/` або `.temp/`; запис історії міграцій у специфікацію |
| **`/cleanup`** | Lifecycle (Stage 8) | Видалення папок `.temp/<topic>/` після `ask_question` | Видалення без явного підтвердження через `ask_question`; видалення поза `.temp/` |
| **`/using-agent-skills`** | Meta-Router | **Жодних (100% Read-Only)** | Створення/зміна будь-яких файлів |
| **`/debug`** | Utility | Мінімальний фікс + регресійний тест після діагностики | Хаотичне вгадування без відтворення і локалізації; додавання фіч при поламаному білді |
| **`/git`** | Utility | `git add`, `git commit` після підтвердження плану | Індексація/коміт `.temp/`; виконання `git commit` або `git push` без згоди користувача |

### 2.2. Протокол визначення активної теми (`.temp/<topic>/` Resolution)

Усі скіли, що працюють із `.temp/`, використовують єдиний детермінований алгоритм:

1. Якщо в `.temp/` існує рівно **1 папка теми** або назва теми однозначно випливає з поточного чату — тема обирається автоматично з виведенням рядка `Active topic: .temp/<topic>/`.
2. Якщо в `.temp/` існує **2 або більше папок тем** і з контексту чату неможливо однозначно визначити цільову тему — агент виводить перелік наявних тем і запитує користувача.
3. Перед створенням першого файлу в `.temp/` агент перевіряє наявність рядка `.temp/` у кореневому `.gitignore` і додає його за потреби.

---

### 2.3. Протокол інтерактивних розвилок (Interactive Advisor Loop)

На вході (Prerequisite Advisor) та на виході (Forward Handoff) кожен скіл дотримується контракту:

1. Надає повний перелік релевантних варіантів дій.
2. Позначає оптимальний варіант як **`(Recommended)`** із коротким обґрунтуванням.
3. Дозволяє користувачу поставити уточнюючі запитання або запитати про плюси й мінуси варіантів; після надання пояснення агент **обов'язково повторно виводить варіанти для вибору**.
4. **Terminal Turn Rule**: Після виведення розвилки агент негайно зупиняє свій хід і очікує рішення користувача.

---

### 2.4. Контракт еволюції коду та неруйнівної декомпозиції

1. **Стратегія інтеграції в `/proposal`**:
   * При зміні існуючих методів, класів або публічних контрактів агент пропонує вибір між:
     * **Parallel Implementation (Expand-Contract)**: створення нової реалізації поруч зі старою → перемикання клієнтів після повної готовності → визначення політики щодо старого коду (**Deprecate** або **Remove**).
     * **Direct In-Place Replacement**: пряма заміна (лише для локальних неруйнівних змін).
2. **Імутабельність та пріоритет файлів задач у `/decompose` та `/implement`**:
   * `/decompose` ніколи не перезаписує створені файли задач. Кожна нова ітерація створює окремий файл: `tasks.md` (первинний), `review-1-tasks.md`, `review-2-tasks.md` (за підсумками `/review`), `subtasks-<id>.md` (при дробленні задачі).
   * `/implement` обирає активний файл із невиконаними задачами (`- [ ]`) за пріоритетом: `subtasks-*.md` → `review-<N>-tasks.md` (з найбільшим `N`) → `tasks.md`.
   * Коли в `subtasks-<id>.md` закривається остання задача (`[x]`), `/implement` автоматично синхронізує статус відповідної батьківської задачі (`[ ]` → `[x]`) в основному файлі задач.
   * Після виконання кожної окремої задачі проєкт залишається в 100% робочому стані (компілюється і проходить тести).

---

### 2.5. Контракт дистрибуції та встановлення репозиторію

Репозиторій підтримує як локальне (проєктне), так і глобальне встановлення:

* **`skills/<name>/SKILL.md`**: канонічна директорія всіх 12 скілів для сумісності з `npx skills add` (локально та `--global`), `agy plugin install`, `gemini skills install` та `cmd skills add`.
* **`.agents/skills/<name>/SKILL.md`**: локальна копія скілів для роботи всередині воркспейсу самого репозиторію (синхронізується командою `.\install.ps1 -SyncRepo` або `./install.sh --sync-repo`).
* **`plugin.json`**: кореневий маніфест плагіна Antigravity.
* **`install.ps1` / `install.sh`**: скрипти встановлення з підтримкою прапорців `-Global` / `--global`, `-Target <path>` / `--target <path>`, `-Skill <name>` / `--skill <name>` та `-SyncRepo` / `--sync-repo`.

## 3. Інваріанти поведінки (Behavioral Invariants)

* **Always**:
  * Спілкуватися з користувачем і створювати артефакти в `.temp/` мовою звернення користувача; вести `docs/specifications/` мовою документації проєкту.
  * Перевіряти точні версії бібліотек у маніфестах проєкту (`package.json`, `.csproj`, `Cargo.toml`, `pyproject.toml`, `go.mod`) перед проектуванням (`/proposal`) або написанням коду (`/implement`).
  * Зберігати проєкт у 100% робочому стані після кожної окремої задачі.
* **Never**:
  * Ніколи не створювати тимчасові файли розробки (`SPEC.md`, `tasks/`, `docs/intent/`) поза `.temp/<topic>/`.
  * Ніколи не виконувати запис або видалення файлів під час роботи read-only скілів (`/idea`, `/interview`, `/review`, `/using-agent-skills`).
  * Ніколи не індексувати і не комітити директорію `.temp/` у Git.
